The plugin uses [@wordpress/env](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-env/) to provide a consistent, containerized WordPress development environment. This is useful for local development and CI/CD pipelines where a full WordPress installation is required.

After a fresh repository clone, install the project dependencies, build the assets, and start the environment:

```bash title="Terminal"
composer install
npm ci
npm run build
npm run env:start
```

Composer dependencies and compiled assets are explicit development prerequisites. The wp-env lifecycle deliberately does not generate either one.

If either generated Composer autoloader is missing, Demo Plugin calls `wp_trigger_error()` with `E_USER_WARNING` and stops loading. WordPress therefore remains usable, while development environments with `WP_DEBUG` enabled surface the missing setup step. Run `composer install`, then start wp-env again.

:::note
WP-CLI is treated as an environment dependency. Commands such as `composer run i18n:extract` and `composer run i18n:compile` assume that `wp` and the required WP-CLI packages are already available in the active environment. If you run the commands outside `wp-env`, install WP-CLI yourself. See the [official WP-CLI installation guide](https://make.wordpress.org/cli/handbook/guides/installing/).
:::

## Configuration

See `.wp-env.json` for the configuration. The setup uses `mappings` instead of the common `plugins: ["."]` approach and runs the containers with PHP 8.1 or newer so WP-CLI i18n commands support the `make-php` compilation step.

Application tests use the isolated `.wp-env.test.json` configuration. Both environments automatically select available ports to avoid collisions with other local projects.

### Why `mappings` instead of `plugins: ["."]`

The standard approach maps the current directory as a plugin, but the resulting folder name depends on the parent directory name. This causes issues when:

- Different developers have different folder names for their checkout
- CI/CD environments use unpredictable directory names
- WP-CLI commands need to target the plugin by name

Using explicit `mappings` with a hardcoded plugin name ensures deterministic paths and reliable WP-CLI targeting across all environments.

## Available Scripts

Scripts that interact with wp-env are defined in `package.json`:

| Script | Description |
|--------|-------------|
| `npm run env:start` | Start the Docker containers |
| `npm run env:stop` | Stop the Docker containers |
| `npm run env:destroy` | Remove containers and data |
| `npm run env:cli` | Run commands inside the container |
| `npm run env:test:start` | Start the isolated application-test environment |
| `npm run env:test:stop` | Stop the isolated application-test environment |
| `npm run test:php` | Start the test environment and run PHPUnit application tests |

### Running Commands Inside wp-env

The `env:cli` script is pre-configured with the correct working directory:

```bash title="Terminal"
npm run env:cli -- composer run i18n:compile
npm run env:cli -- composer run phpstan
```

On every `env:start`, the `afterStart` hook activates Demo Plugin in the `cli` container. It does not run Composer or wp-scripts. Run `composer install` for PHP dependencies and `npm run build` for compiled scripts, styles, blocks, and referenced images.

If Composer is not installed on the host, start wp-env without lifecycle scripts, install inside the container, and then start normally to activate the plugin:

```bash title="Terminal"
npm run env:start -- --no-scripts
npm run env:cli -- composer install
npm run env:start
```

Application tests use a separate wp-env configuration rather than the deprecated implicit `tests-cli` environment. `npm run test:php` starts that environment automatically and runs PHPUnit in its `cli` container.

## Adding Custom Scripts

**Host-side scripts** (interacting with wp-env from outside) belong in `package.json`:

```json title="package.json"
{
  "scripts": {
    "env:my-script": "wp-env run cli my-command"
  }
}
```

**Container-side scripts** (executed inside wp-env) belong in `composer.json` because Composer is available inside the container but npm is not:

```json title="composer.json"
{
  "scripts": {
    "my-script": "wp some-command"
  }
}
```

Then run it with:

```bash title="Terminal"
npm run env:cli -- composer run my-script
```

## Usage in CI/CD

The plugin uses wp-env in the deploy workflow to compile translations. This requires a full WordPress environment with WP-CLI available.

## Things to Keep in Mind

- Docker must be installed and running
- Node.js and npm are needed to install and run `@wordpress/env` and compile assets
- Composer dependencies must be installed before Demo Plugin can load; Composer may run on the host or inside wp-env
- wp-env automatically selects available ports, so the URLs can differ between starts; use `npm run env:cli -- wp option get home` when a script needs the current URL
- The first start downloads WordPress core, so it may take a few minutes
- Data persists between starts unless you run `env:destroy`
- The `afterStart` lifecycle script activates the plugin but does not install dependencies or build assets
- The PHP version is pinned to 8.1 because `composer run i18n:compile` uses `wp i18n make-php`
